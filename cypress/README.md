# Coral-Arches Cypress E2E — running the suite and what it covers

The working guide for the end-to-end suite in `cypress/`: how to get a local stack
into a state the specs can actually run against, how to run them, what each spec
exercises, and the known blockers.

---

## 1. TL;DR

Assuming the dev stack is already up and seeded:

```bash
cd /home/dylan/Development/coral/coral-arches

# interactive runner
npx cypress open

# one spec, headless (the normal way to work)
npx cypress run --spec cypress/e2e/02_flag_for_enforcement/flag_for_enforcement_workflow.cy.js

# the whole suite
npx cypress run
```

Before running anything on a fresh database, see [§2 Prerequisites](#2-prerequisites),
[§3 Authentication](#3-authentication--forced-2fa) and [§4 Seed data](#4-seed-data) —
without the TOTP device the login never completes, and without seed data every
workflow launcher comes up empty.

Before running the *whole* suite, read
[§7 Cross-spec state](#7-cross-spec-state-the-suite-shares-one-database). Expect it to
take a long time and a lot of RAM.

## 2. Prerequisites

### 2.1 The app stack

The specs drive a real Arches instance; there is no mocking anywhere. The local dev
stack is the toolkit compose file under `docker/` (a git submodule), driven from the
root `Makefile`:

```bash
make run           # docker compose up (project name: coral)
make down
make manage CMD="migrate"      # runs manage.py inside arches_worker
make webpack                   # npm run build_development inside the container
```

Containers you should see: `coral-arches-1`, `coral-arches_worker-1`, `coral-db-1`,
`coral-elasticsearch-1`, `coral-rabbitmq-1`, `coral-cantaloupe-1`.

Checklist before running any spec:

| Requirement | Why | Check |
|---|---|---|
| App answers on `http://localhost:8000` | `cypress.config.js` `baseUrl` | `curl -so /dev/null -w '%{http_code}' http://localhost:8000/auth/` → `200` |
| Webpack bundle built | Pages render blank/500 otherwise | `make webpack` |
| **Celery worker running** (`coral-arches_worker-1`) | `03_ha_designation` waits on the `remap_monument_to_revision` task; notifications also go through it | `docker ps` |
| Elasticsearch healthy | Every workflow launcher searches ES, not Postgres | `curl localhost:9200/_cluster/health` |
| Resource models **active** | Inactive graphs reject every tile save ("Verify model status is active") | see below |
| `frontend_configuration/` present in the checkout | `tsconfig.json` does `"extends": "./frontend_configuration/tsconfig-paths.json"`; without it *every* spec fails to compile before running a single assertion | `ls frontend_configuration/` → `tsconfig-paths.json`, `urls.json`, `webpack-metadata.json` |

`frontend_configuration/` is gitignored and generated by Arches at app startup
(`arches/apps.py` `AppConfig.ready()`). Locally the repo is volume-mounted into
`coral-arches-1`, so it appears in the checkout by itself once the app has booted.
(In CI it has to be `docker cp`'d out of the container — see [§8](#8-how-ci-runs-it).)

Activating models on a freshly bootstrapped database:

```bash
make manage CMD='shell -c "from arches.app.models.models import GraphModel; \
print(GraphModel.objects.filter(isresource=True, draft=None, publication__isnull=False).update(is_active=True))"'
```

### 2.2 Cypress itself

Cypress is **not** an npm dependency of this repo — `package.json` has no `cypress`
entry. `npx cypress` fetches it and caches the binary under `~/.cache/Cypress/`


```bash
npx cypress@15.18.1 run --spec <path>
```

## 3. Authentication — forced 2FA

Coral has a **custom login view**
(`coral/views/auth.py` `LoginView.post`) that forces two-factor on *every* login,
regardless of `ENABLE_TWO_FACTOR_AUTHENTICATION` / `FORCE_TWO_FACTOR_AUTHENTICATION`
(both `False` in settings). There is no plain username/password path:

- user has a confirmed device → renders `two_factor_token.htm`, asking for `otp_token`
- user has no device → redirects into forced 2FA *setup* (which auto-creates an
  unconfirmed `TOTPDevice`, which is why deleting admin's device just regenerates one)

The suite solves this by seeding admin a **confirmed TOTP device with a known
secret** — the RFC 6238 test key, hex `3132333435363738393031323334353637383930`:

```bash
make manage CMD="seed_test_totp"        # idempotent; --username defaults to admin
```

`cypress.config.js` implements a matching `generateOtp` node task (plain
`crypto` HMAC-SHA1 TOTP, no npm dependency) and `cy.login()` types the generated
code into `input[name="otp_token"]`.

Two consequences worth knowing:

- The device has replay protection (`last_t`), so **two logins inside the same 30s
  window collide**. That is why `cy.login()` wraps everything in
  `cy.session('admin', …, { cacheAcrossSpecs: true })` — the real login happens once
  per run.
- The device lives in the database, so **re-run `seed_test_totp` after any DB
  recreate**.

## 4. Seed data

The specs were written against a populated development database. A freshly
bootstrapped one has **zero Heritage Assets** (`coral/pkg/business_data` ships only
groups, permissions and sets), so every workflow launcher comes up empty and
everything that opens an existing record fails.

There are four seeding steps. On a long-lived local dev DB you may already have
suitable data and can skip most of them; on a fresh DB you need all four.

### 4.1 Baseline Heritage Assets — `cypress/seed/seed.py`

```bash
python3 -m venv .venv && ./.venv/bin/pip install -r cypress/seed/requirements.txt

./.venv/bin/python cypress/seed/seed.py \
  --pkg-dir coral/pkg \
  --graphs "Heritage Asset" -n 9 \
  --only-aliases monument_name,resourceid,smr_number,ihr_number,hb_number,historic_parks_and_gardens \
  --overrides cypress/seed/coral_e2e_overrides.json \
  -o seeded.json

# then, inside the arches container
make manage CMD="packages -o import_business_data -s /path/to/seeded.json -ow overwrite"
```

What comes out (`cypress/seed/coral_e2e_overrides.json` pins the literals the specs
match on):

| # | Site Name | HA Number | SMR | Display name | Used by |
|---|---|---|---|---|---|
| 1–3 | Testing | HA/01–03 | — | `HA/01 Testing` … | `02_flag_for_enforcement` (HA/02), `07_incident_report` (HA/03), `08_agri` (HA/02) |
| 4–6 | Testing | HA/04–06 | SMR-TEST-004… | `SMR-TEST-004 Testing` … | `09_state_care` (launcher searches for non-null SMR) |
| 7–9 | Garden Test | HA/07–09 | — | `HA/07 Garden Test` … | `01_add_garden`'s three "open an existing HA" tests |

Every flag is load-bearing — `cypress/seed/README.md` explains each one. The short
version:

- **`-n 9`** — Arches sets `minimumResultsForSearch: 5`; below that selectWoo hides
  the select2 search box entirely and `cy.type()` fails with "element is not visible".
- **`--only-aliases`** — an unrestricted run generates all 74 tiles and fires coral
  post-save functions on synthetic data they were never written for (two crash).
- **`--overrides`** — the specs pick dropdown options by literal text.
- **`display_name` is deliberately not seeded** — `generate_ha_name_function` creates
  that tile itself; supplying one gives two tiles for a cardinality-1 nodegroup and
  the import fails with `TileCardinalityError`.

Caveats: **HA numbers must be unique** (`coral/utils/ha_number.py:validate_id`
enforces it) — on a development database `HA/01`–`HA/09` are usually taken, so pick a
spare range like `HA/91`+. And **re-running is not idempotent**: resource ids are
UUID5-derived, so a second import after a *failed* one leaves partial tiles and trips
`TileCardinalityError`. Delete the resources first.

### 4.2 Management commands

```bash
make manage CMD="seed_test_ha"             # gives an HA an SMR Number + reindexes it → unblocks 09_state_care
make manage CMD="seed_test_issue_report"   # puts ISSUE-TEST-001 on HA/03 → unblocks 07_incident_report
```

`seed_test_ha` reindexes into Elasticsearch because the State Care launcher runs an
*advanced search* for a non-null SMR Number — a DB-only write is invisible to it.

### 4.3 Resources the specs create for each other

`01_create_a_person`, `02_create_an_organisation` and `03_create_a_bibliographic_source`
are not really assertions — they are **fixtures expressed as specs**. They create
`Test Person`, `John Doe`, `John Smith`, `Test Organisation` and `Test Bibliographic`
if missing, and later specs pick those by name (`04_licensing` uses `John Smith` and
`Test Person`; `02_flag_for_enforcement` asserts on `Test Organisation`). Run them
first on a fresh database.

## 5. Running the tests

### 5.1 Interactive

```bash
npx cypress open
```

Pick E2E → Electron → a spec. Best for developing or debugging a single spec: you get
time-travel snapshots, the command log, and live reload on save.

### 5.2 Headless, one spec (recommended for a check)

```bash
npx cypress run --spec cypress/e2e/05_fmw_inspection/fmw_inspection_workflow.cy.js
```

Add `--config video=false` to skip video encoding. Keep video on when you need to see
what the data looked like *mid-run* — the failure screenshot only captures the last
frame.

Don't batch specs on a laptop — the stack alone sits around 12 GB.

### 5.3 Whole suite

```bash
npx cypress run
```

### 5.4 Pointing at a different app

```bash
CYPRESS_BASE_URL=http://other-host:8000 npx cypress run
# or
npx cypress run --config baseUrl=http://other-host:8000
```

### 5.5 Reproducing the CI run exactly

CI runs Cypress in a container on the compose network. To do the same locally against
the host stack:

```bash
docker run --rm --name cy_run --network host \
  -v "$PWD":/e2e -w /e2e \
  cypress/included:15.18.1 \
  --browser electron --config video=false \
  --spec cypress/e2e/05_fmw_inspection/fmw_inspection_workflow.cy.js
```

`--network host` lets the container reach the app on `localhost:8000`; `--name cy_run`
makes it killable with `docker rm -f cy_run`. Files the container writes are
root-owned — fix them the way CI does:

```bash
docker run --rm --entrypoint sh -v "$PWD":/e2e cypress/included:15.18.1 \
  -c "chown -R $(id -u):$(id -g) /e2e/cypress"
```

### 5.6 Artifacts

`cypress/videos/` and `cypress/screenshots/`, both gitignored.

### 5.7 Config worth knowing (`cypress.config.js`)

| Setting | Value | Why |
|---|---|---|
| `baseUrl` | `http://localhost:8000` | Override per [§5.4](#54-pointing-at-a-different-app) |
| `defaultCommandTimeout` | 12000 | Arches widgets render lazily |
| `pageLoadTimeout` | 90000 | Some workflow steps initialise server-side |
| `experimentalMemoryManagement` | true | The licensing spec can hold the browser for 5+ minutes; without this the Electron renderer runs out of heap and takes the rest of the spec with it |
| `chromeWebSecurity` | false | Cross-origin iframes in report/map components |
| `specPattern` | `cypress/e2e/**/*.{js,jsx,ts,tsx}` | Note: **any** JS file under `e2e/` is a spec |
| `generateOtp` task | node `crypto` TOTP | See [§3](#3-authentication--forced-2fa) |

## 6. What the suite covers

26 active tests plus one documented skip, across 14 spec files. Everything is
UI-driven against a live app: no stubs, no `cy.intercept` mocking. The subject under
test is really the **coral workflow plugins** — their launchers, step ordering,
required-field gating, server-side initialisation, generated identifiers, post-save
functions and summary rendering.

### 6.1 Fixture specs

| Spec | Tests | What it does |
|---|---|---|
| `01_create_a_person.cy.js` | 3 | Creates `Test Person`, `John Doe`, `John Smith` on the Person graph (`22477f01-…`) via `/add-resource`, search-first so it is idempotent |
| `02_create_an_organisation.cy.js` | 1 | Creates `Test Organisation` on the Organization graph (`d4a88461-…`) |
| `03_create_a_bibliographic_source.cy.js` | 1 | Creates `Test Bibliographic` through the *Bibliographic Source Citation* relationship widget. Uses the dropdown's own "Create a new Bibliographic Source…" affordance as the existence check — the previous `/search` scrape always missed (seeded records are provisional) and piled up duplicates |

### 6.2 Workflow specs

| Spec | Tests | Workflow / launcher | Focus and dependencies |
|---|---|---|---|
| `01_add_garden/` | 4 | Add Garden | 1 test creates a **new** HA end to end; 3 open an existing **`Garden Test`** asset and drill into the Heritage Asset Details, Location Details and Finish tabs. Asserts the HA Number field is generated and disabled. A Map-tab test is commented out. |
| `02_flag_for_enforcement/` | 7 | Flag for Enforcement | The richest assertion set. One full pass then six minimal passes, each populating exactly one field, verifying the **Enforcement Summary** renders it. Checks the auto-generated Enforcement ID is non-empty, that `Associated Resources` reads exactly `HA/02 Testing`, and that Flagged By accepts a Person, an Organisation, or both (`Test Person, Test Organisation`). |

Then walks 8 tabs and fills 8 approval dates. Needs a running worker. |
| `04_licensing/` | 3 | `licensing-workflow` | Full application, **licence transfer**, and **licence extension**. The "Initialise Excavation Licence" step is server-side and gets slower as Licence resources accumulate — `workflowNext({timeout: 360000})`. The slowest and most fragile spec. |
| `05_fmw_inspection/` | 1 | FMW Inspection | Report tab (SMR relationship, Land Use, condition/risk scores, owner/occupier/warden), an **Irish Grid TM65 coordinate** entry, documentation, sign-off. |

| `08_agri/` | 1 | Agriculture & Forestry Consultation | The most thorough single test. | `10_risk_assessment/` | 0 (1 `it.skip`) | Risk Assessment | **Blocked, deliberately skipped** — see [§9](#9-known-blockers). Previously an empty body reporting a false pass. |
| `11_ranger_inspection/` | 1 | `ranger-inspection-workflow` | Related HAs, weather/ground conditions, arrival/departure times, boolean radio widgets, an inspection detail sub-tile (Add), review/submission dates. |

### 6.3 What is *not* covered

- No API/unit-level testing here (that is `tests/` and `vitest`).
- No permission or role testing — everything runs as `admin`.
- Map/geometry drawing is largely commented out (`01_add_garden`'s Map tab).
- Letter/document generation is blocked (`08_agri`) — templates under `coral/docx`
  are gitignored deployment assets.
- Search itself is only exercised incidentally, via launchers.

## 7. Cross-spec state: the suite shares one database

There is **no database reset between specs**. Nothing is transactional, nothing is
torn down. This is the single biggest source of "passes locally, fails in the full
run" confusion.

The concrete failure mode already hit once: merely *opening* an existing Heritage
Asset in a workflow rewrites its display name, and if the spec then fails part way
through, the asset is left with a **blank** name. `01_add_garden`'s three
"open an existing HA" tests did that to HA/01–03, and `02_flag_for_enforcement`
— which runs later — then found an unnamed option where it expected `HA/02 Testing`.

Rules that follow:

1. A spec that **mutates** a seeded resource gets **its own instances** in
   `coral_e2e_overrides.json` (that is why `Garden Test` = HA/07–09 exists), matched
   by a search term no other spec uses.
2. Never let two specs assert on the same seeded asset.
3. **Spec execution order is not the directory numbering** — read the run log.
4. Accumulated data slows things down. Licence resources in particular make
   `04_licensing`'s init step dramatically slower over time; prune them or recreate
   the DB if that step starts timing out.

## 8. How CI runs it

`.github/workflows/cypress.yml`, triggered on PRs into `dev`/`main` and by
`workflow_dispatch`. It uses a dedicated `docker-compose.ci.yml` **at the repo root**
(not under `docker/` — that is a submodule, so files added there never reach CI), and
step-driven orchestration rather than GH Actions `services:` (services start before
steps, so they cannot run the post-bootstrap seeds).

The sequence, which doubles as a checklist for reproducing CI locally:

1. `compose up -d --build` — Arches boots with `ALLOW_BOOTSTRAP=True` +
   `INSTALL_CORAL_PACKAGE=True`. **A fresh bootstrap takes ~15 minutes**; the
   `health=starting` loop is not a hang.
2. Wait on the arches healthcheck.
3. Assert the dependency set: `arches` 8.x, `arches-modular-reports==1.0.0b9`, and
   **no `arches-vue-components`** (it clashes with `arches-component-lab` —
   duplicate `WidgetMapping.widget` reverse accessor → `fields.E304`, and Django
   refuses to start).
4. `webpack --config ./webpack/webpack.config.dev.js`.
5. Verify `/auth/` returns 200.
6. `createcachetable`.
7. Activate all resource models.
8. Run `seed.py` and `import_business_data` (the CI image COPYs the checkout rather
   than mounting it, so the JSON is handed over with `docker cp`).
9. Verify the seeded assets are **searchable in Elasticsearch** — a direct ES query
   for each of the three display names.
10. `seed_test_issue_report`, `seed_test_totp`.
11. `docker cp` the generated `frontend_configuration/` out of the container into the
    checkout the Cypress container mounts.
12. Run `cypress/included:15.18.1` on the compose network against
    `http://arches:8000` (same origin, so `SameSite=Strict` cookies work).
13. Upload screenshots (on failure) and videos (always); dump arches + celery logs on
    failure.

Two environment details are load-bearing:

- **`DJANGO_INSECURE_COOKIES=True`** — otherwise session/CSRF cookies are marked
  `Secure`, get dropped over plain http, and login breaks.
- The checkout uses `path: coral` so the Dockerfile's parent-directory build context
  finds the `coral/` subdir.

Note CI does **not** run `seed_test_ha`; `09_state_care` relies on the SMR numbers
that `seed.py` puts on HA/04–06.

### Debugging a CI failure

```bash
gh run download <run-id> -n cypress-videos
```

The screenshot only captures the final frame — the video is what shows you the data
state earlier in the run. Extracting a contact sheet works well:

```bash
ffmpeg -i spec.mp4 -vf "fps=1,crop=...,tile=5x9" sheet.png
```

(the ffmpeg binary from a venv-installed `imageio-ffmpeg` is fine).

## 9. Known blockers

**`10_risk_assessment` — cannot be fixed in spec code.**
`open-risk-assessment-workflow.js` (`stateMonumentString`) filters HAs on node
`74ef37e0-37b5-11ef-9263-0242ac150006` == concept value
`8da10724-1bd3-c095-6d4d-fb8657574b40`. Neither that value nor the node's
rdmCollection `34573061-2a22-decd-e2e3-559791d35efa` exists in the loaded reference
data, and Arches rejects writing it ("This UUID is not an available concept value").
The dropdown always says "No results found" and Start New stays disabled. Fix needs
the missing reference data loaded, or the plugin's hard-coded concept id corrected.

**`08_agri` — letter generation.** `/filetemplate` 404s because the `.docx`
templates live in the gitignored `coral/docx`; with a template present it then 500s
in `coral/views/file_template.py` (`GenericTemplateProvider.get_mapping` calls
`resource.items()` on a querysets_shim resource). The spec asserts up to the Letter
Type selection and carries the enabling code in a comment.

**`08_agri` — "Cur E" sign-off.** The `user-to-model-select` widget only enables
itself when the logged-in user's Person resource belongs to one of the step's
`signOffGroups`. Those Group resources do not exist in a bootstrapped database, and
`Person.where(user_account=…)` cannot match anyway — querysets_shim resolves a node
that is its own nodegroup one level too deep. The spec asserts the card renders.

## 10. Custom commands

All in `cypress/support/commands.js`. **Prefer these over hand-rolled selectors** —
they encode workarounds for real Arches 8.2 behaviour.

| Command | Notes |
|---|---|
| `cy.login()` | Username/password + generated TOTP, wrapped in `cy.session(…, {cacheAcrossSpecs: true})`. |
| `cy.workflowNext(opts)` | Clicks the footer forward button and **asserts the step counter advanced**. Must stay a retrying query chain — several transitions only enable the button after a slow backend step. Default 60s. |
| `cy.fillDate(cardClass, date='28-07-2026')` | **Types** into the datepicker. Clicking `.input-group-addon.date-icon` opens no picker and leaves the field empty. `{enter}` blurs, so don't chain `.blur()`. |
| `cy.typeInCard(cardClass, text)` | Scroll, clear, type, assert value. |
| `cy.pickCardOption(cardClass, index=0)` | Select2 inside a named card. |
| `cy.pickOptionByLabelPrefix(prefix, indexOrText=0)` | For widgets whose `aria-label` embeds the **current value** ("Condition Score, 2"). String arg picks by option text, number by index. |
| `cy.pickDomainByLabel(prefix, optionText)` | Domain-value selects. |
| `cy.openRelationship(ariaLabel)` | Opens a resource-instance dropdown, retrying up to 4 times — select2 renders a zero-size span until scrolled. |
| `cy.pickRelationshipFirst(ariaLabel)` | First *real* option. |
| `cy.pickRelationshipByName(ariaLabel, name, maxScrolls=15)` | Scrolls the paginated list looking for an exact text match. |
| `cy.select2Search(term)` | Types into the dropdown's search box, or logs and falls through when selectWoo hid it (<5 results). |
| `cy.type_ckeditor(name, content)` / `cy.typeRichText(cardClass, content)` | CKEditor 4 instances are not real inputs — drive them through `CKEDITOR.instances`. |

`Cypress.on('uncaught:exception')` currently returns `false` globally — app errors
never fail a test. That is a deliberate temporary measure and worth revisiting.

## 11. Writing and fixing specs — the drift patterns

These are the recurring causes of breakage after the Arches 8.2 upgrade. Check them
before assuming a real regression.

- **Deep structural selectors have all drifted.** Anything like
  `> .row > .form-group > [style="display: flex; gap: 8px;"] > …` is fragile by
  construction. Use `.card_component.<name> input` or a custom command.
- **Hard-coded aria-label values break** — the label carries the live value. Match on
  the `"<label>, "` prefix.
- **`cy.click({multiple:true}, {force:true})` is a bug.** `click()` takes one options
  object; two args are read as `(position, options)`, so `multiple` is silently
  dropped and it throws on multi-element subjects. Use
  `click({force: true, multiple: true})`.
- **Back-to-back `workflowNext()` with no wait** re-clicks a stale button and silently
  skips a tab. Always wait between steps.
- **Dropdown "first option" picks must exclude** `.loading-results`,
  `.select2-results__option--load-more` and `.select2-results__message`. Picking the
  placeholder leaves the launcher empty, which keeps "Start New" disabled — a
  confusing, silent failure.
- **The last workflow tab's footer button is a plain "Save"**, not a forward step, so
  `workflowNext()` will not match it. Use the
  `contains(/Save and Continue|Next Step|Save/)` form.
- **Blanket final `.btn-success` clicks race the completion re-render**
  ("element detached"). Target the footer or `.workflow-top-control` explicitly.
- **A launcher's "Start New" may navigate away** rather than open in place, and some
  workflows set `disableStartNew` so the button never renders at all.
- **Fix the test, not the app.** If a spec exposes a real backend bug, report it —
  don't patch app source to make the assertion pass.

## 12. Troubleshooting

| Symptom | Cause |
|---|---|
| Every spec fails before running: `File './frontend_configuration/tsconfig-paths.json' not found` | Generated dir missing from the checkout — a compile error, not an assertion failure. See [§2.1](#21-the-app-stack). |
| Login loops or lands on 2FA setup | `seed_test_totp` not run, or run against a DB that has since been recreated. |
| Login fails intermittently mid-suite | TOTP replay protection — two real logins in the same 30s window. `cy.session` should prevent this; check it wasn't bypassed. |
| Launcher dropdown empty / "Start New" disabled | No seed data, models not activated, or the first option picked was the loading placeholder. |
| Tile saves 500 with "Verify model status is active" | Resource models not activated. |
| `03_ha_designation` never finds a revision | Celery worker not running. |
| `04_licensing` times out at `startLicensing` | Environment, not spec logic — memory pressure or accumulated Licence resources. Restart `coral-arches-1`, consider pruning. |
| "We detected that the Electron Renderer process just crashed" | Memory. `experimentalMemoryManagement` is already on; run one spec at a time. |
| Passes solo, fails in the full run | Cross-spec contamination — [§7](#7-cross-spec-state-the-suite-shares-one-database). |
| `ModuleNotFoundError: arches_modular_reports` on app boot | Container venv predates the dependency. `docker exec` into `coral-arches-1`, `pip install arches-modular-reports arches-search`, restart. Note this lives in the writable layer — it does not survive `docker compose down`. |
